## 4. LingBot-MAP CPU 추론 실측 (2026-07-11)

GPU 없이 로컬 맥에서 3D 재구성이 **실제로 동작함을 확인**. crash1(4초 영상, 40프레임)으로 측정.

| 항목 | 값 |
|---|---|
| 장비 | Apple Silicon Mac, PyTorch 2.13 CPU (SDPA attention, ~1.7코어 활용) |
| 입력 | crash1 40프레임 @ 518px, streaming 모드 |
| 순수 추론 | **8분 25초** (평균 15.8 s/프레임) |
| 전체 파이프라인 (모델로드+추론+스카이분할+마스킹+지면정렬+저장) | **10분 58초** |
| 산출물 | scene.splat 44.6 MB (146만 점) + vehicles.json (ego+13대, 충돌·스케일 임베드) |
| 참고: RTX A5000 (동일 모델) | ~20 fps — 40프레임 ≈ 2 s (약 **250×** 차이) |

**주의 — 프레임당 시간이 비선형 증가**: 초반 ~5 s/프레임 → 40프레임째 ~42 s/프레임 (KV 캐시 누적). 긴 영상(200프레임+)은 CPU로 수 시간 소요 예상 → **CPU는 10초 이하 짧은 클립 전용**.

**CPU 특이사항**: fp32 추론에서 신뢰도 출력이 ~1.0에 밀집 (GPU bf16과 분포 상이, p5/p50/p95 = 1.000/1.000/1.001) → `--conf_threshold 1.0` 필요 (GPU 기본 2.0은 전부 걸러버림). 업로드 서버는 `LINGBOT_CONF_THRESHOLD` env로 제어(기본 1.0).

**결론**:
- 데모·개발·짧은 클립(≤10초): **CPU로 충분** — 업로드 후 10~15분 배치 잡으로 완전한 3D 사고 재현 산출
- 실서비스·긴 영상·다건 처리: **GPU 워커 필요** (동일 코드, `LINGBOT_MODEL_PATH`만 서버 GPU로)
- 산출물 품질: 동일 모델·가중치이므로 재구성 결과는 장치와 무관 (뷰어 육안 확인 완료)
- 동시 실행 금지: CPU 추론 2개 병행 시 서로 ~5배 지연 + 메모리 압박으로 강제종료 실측 → 업로드 서버는 잡 직렬화(기본 1개)

## 5. 스플랫 품질 개선 실측 (crash1, 원본 영상 대조)

원본 프레임과 재구성 결과를 직접 비교해 확인한 주요 열화 원인 2건과 수정 효과:

| 문제 | 원인 | 수정 | 효과 (개선 전 → 후) |
|---|---|---|---|
| 도로 위 빨간 얼룩 줄무늬 | ego 보닛(프레임 하단 25%)이 매 프레임 역투영 | 시간적 정적 픽셀 마스크 (보닛·타임스탬프·워터마크, 프레임의 6.2% 검출) | 붉은 점 **13.6% → 7.1%** |
| 주변 구조(나무·가드레일) 소실 | CPU fp32 신뢰도 퇴화 분포(p95−p5=0.0008)에서 임계 비교가 무작위 필터로 작동 | 퇴화 분포 자동 감지 → 마스크만 적용 | 유지 점 **1.47M → 2.99M (2배)** |
| 점이 덩어리져 보임 | 뷰어 고정 점 크기(0.05유닛) vs 씬 스케일 임의(~1유닛) | 점 크기 = 씬 최대치수 × 0.5% | 도로·수목 구조 식별 가능 |

**남은 품질 한계와 로드맵**: ① 처리 해상도 518px(원본 1280+ 대비) — 해상도 ↑ 시 CPU 시간 ~2×, GPU 권장 ② 잔여 붉은 점 7.1%는 진동으로 마스크를 벗어난 보닛 가장자리+실제 붉은 물체 ③ 4초/40프레임의 짧은 커버리지는 데이터 한계 ④ 포토리얼 품질은 3DGS 학습 경로(10_3dgs) 재시도 필요 (LingBot 포즈+dense 초기화).
