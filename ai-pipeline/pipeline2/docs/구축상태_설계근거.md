> "이건 왜 있어야 하고, LingBot-Map이 어떻게 되어 있어서 이렇게 만들었는가"를
> 단계별로 설명하는 문서. 코드를 읽기 전에 **왜 이런 구조인지**를 먼저 잡기 위함.

작성 기준일: 2026-06-04 / 브랜치: `refactor/v2-pipeline`

## 0. 한 줄 요약

iPhone 단안 MOV 한 개 → **LingBot-Map**으로 포인트클라우드+카메라포즈를 뽑고 →
노이즈 제거·지면 정렬 → **3DGS** 학습 → **웹**에서 splat + 차량 경로 애니메이션.

기존 `src/` 12단계(COLMAP SfM 기반)를 **대체**하는 새 4단계 파이프라인.
핵심은 *"COLMAP으로 며칠 걸리던 SfM을 LingBot-Map feed-forward 추론 한 방으로 대체"* 한다는 것.

## 1. 먼저: LingBot-Map이 어떻게 동작하는가 (모든 설계의 근거)

이 부분을 이해하면 아래 모든 "왜"가 풀린다.

### 1-1. 정체
- Ant Group **Robbyant** 팀의 **streaming 3D reconstruction** 모델 (2026.04 공개).
- GitHub `Robbyant/lingbot-map`, HF `robbyant/lingbot-map`, arXiv 2604.14141.
- **feed-forward**: COLMAP처럼 반복 최적화(번들 조정) 없이, 신경망 한 번 통과로
  카메라 포즈 + dense 3D 포인트를 출력. 518×378에서 ~20FPS, 1만 프레임도 처리.
- 클론 위치: `ai-pipeline/third_party/lingbot-map`.

### 1-2. 실제 추론 흐름 (`demo.py` 분석 결과)
```
영상/이미지 → load_images() → load_model() → model.inference_windowed()
            → postprocess() → predictions(dict) → [viser 뷰어로 표시]
```
`postprocess()`가 만드는 `predictions` dict 핵심 키:
| 키 | shape | 의미 |
|---|---|---|
| `world_points` | (S,H,W,3) | 프레임별 픽셀의 **월드 3D 좌표** |
| `world_points_conf` | (S,H,W) | 픽셀별 신뢰도 |
| `extrinsic` | (S,3,4) | **c2w** (postprocess가 closed_form_inverse로 이미 변환함) |
| `intrinsic` | (S,3,3) | 카메라 내부 파라미터 |

### 1-3. 우리가 부딪힌 두 가지 결정적 사실
1. **demo.py는 결과를 디스크에 저장하지 않는다.** 오직 `viser` 인터랙티브
   뷰어(`http://localhost:8080`)로만 띄운다. README가 말한 `--save_predictions`
   플래그는 이 demo.py에 **존재하지 않는다**.
   → 그래서 우리는 demo의 함수만 빌려와 **직접 ply/poses로 저장하는 Stage 1**을 만들었다.
2. **conf는 0~1 스케일이 아니다.** demo 기본 임계값이 1.5다.
   → 그래서 절대 임계 대신 **백분위(percentile) 필터**를 쓴다.

### 1-4. 환경 제약
- LingBot-Map은 **conda py3.10 + torch 2.8.0+cu128** 요구.
- 우리 학습 환경 `3dgs_pipeline`는 **torch 2.4.0+cu121**. → **충돌**.
- 그래서 **env를 분리**할 수밖에 없다 (4장 참고).

## 2. 단계별 "왜 이렇게 만들었는가"

### Stage 1 — LingBot-Map 추론 → ply/poses/images
파일: `stages/stage1_infer.py` (env: `lingbot-map`)

| 설계 | 왜 |
|---|---|
| demo.py의 `load_images`/`load_model`/`postprocess`를 **import해서 재사용** | LingBot 내부 추론 로직을 다시 짜면 미묘한 버그(좌표 규약, dtype, KV캐시) 위험. 검증된 demo 함수를 그대로 호출하는 게 정확. |
| 자체적으로 ply+poses+images **저장기**를 붙임 | (1-3-①) demo는 저장 안 함. predictions를 우리가 직접 직렬화. |
| `extrinsic`을 그대로 c2w로 취급 | (1-2) postprocess가 이미 c2w로 변환해 둠. 추가 역변환 불필요. |
| conf **백분위** 필터(`conf_percentile`) | (1-3-②) conf 스케일이 0~1이 아니라 절대 임계가 의미 없음. 하위 X%를 버림. |
| `points_frame_stride` / `points_pixel_stride` / `max_points` 캡 | 영상이 5438프레임. 10fps로 줄여도 ~1810프레임 × 약 195k픽셀 = **3.5억 포인트**. 그대로 메모리에 못 올림. 프레임/픽셀 솎고 최종 랜덤 캡. |
| `mode: windowed` 기본 | LingBot은 320프레임 RoPE 윈도우로 학습됨. 그 이상은 windowed/keyframe_interval 필수. 1810프레임은 한참 초과. |
| ply를 **numpy로 직접** 작성 (open3d 미사용) | Stage 1은 lingbot env에서 도는데 거기엔 open3d가 없음. numpy 바이너리 PLY 작성기(`common/logio.write_ply_numpy`)로 의존성 최소화. |
| **포즈에 대응하는 이미지도 저장** (`images/`) | 3DGS 학습은 각 포즈에 맞는 RGB 프레임으로 photometric loss를 계산함. LingBot이 쓴 전처리(518 crop) 이미지가 intrinsics와 일치하므로, 그 이미지를 그대로 넘겨야 포즈·내부파라미터·이미지가 일관됨. |

산출물: `01_mapping/{point_cloud.ply, camera_poses.json, images/, meta.json}`

### Stage 2 — 전처리 (노이즈 제거 + 지면 정렬)
파일: `stages/stage2_preprocess.py` (env: `3dgs_pipeline`)

| 설계 | 왜 |
|---|---|
| SOR → Radius → Voxel **순서** | feed-forward 깊이는 경계/하늘/먼 곳에서 튀는 점이 많음. 통계적 이상치(SOR) → 고립점(Radius) → 격자 다운샘플(Voxel) 순으로 빡세게. (요청 스펙: nb50/std2.0, nb10/r0.5, voxel0.05) |
| **RANSAC 지면 평면** 검출 → Y=0 정렬 | LingBot 출력 월드좌표는 첫 프레임 카메라 기준이라 **지면이 기울어 있음**. 웹에서 차량이 "바닥 위를 달리는" 그림이 되려면 지면=Y=0, 위=+Y로 맞춰야 함. |
| 같은 변환 T를 **포인트와 포즈 둘 다**에 적용 | 포인트만 돌리면 카메라 경로가 따로 놀아 splat과 경로가 어긋남. 강체변환을 양쪽에 똑같이 걸어 정합 유지. |
| 법선 **부호를 카메라 위치로 결정** | 평면 법선은 ±방향 모호함. "카메라는 지면 위에 있다"는 사실로 +Y(위)를 확정. 포즈 없으면 +Y 가정. |
| Rodrigues 최소회전으로 법선→+Y | 짐벌락 없이 평면 법선을 +Y에 정렬하는 안정적 회전 (`common/geometry`). |

산출물: `02_preprocess/{point_cloud_clean.ply, camera_poses_aligned.json, transform.json, preview_topdown.png}`

### Stage 3 — 3DGS 학습 (COLMAP 포맷 → 학습 → .splat)
파일: `stages/stage3_train.py` (env: `3dgs_pipeline`)

| 설계 | 왜 |
|---|---|
| LingBot 출력을 **COLMAP 텍스트 모델**로 변환 | `third_party/gaussian-splatting`의 train.py는 COLMAP/Blender 데이터셋만 읽음. LingBot의 ply+poses를 COLMAP `cameras/images/points3D.txt` + `images/`로 바꿔야 학습 가능. |
| c2w → **w2c 쿼터니언**으로 기록 | COLMAP `images.txt`는 world-to-camera(qw,qx,qy,qz, t)를 요구. 우리 포즈는 c2w라 역변환 후 회전→쿼터니언. (테스트로 1e-15 정확 확인) |
| 단일 **PINHOLE** 카메라 공유 | LingBot은 한 카메라(고정 intrinsics)라 프레임마다 카메라를 만들 필요 없음. |
| 정제 ply를 **points3D(초기 가우시안)**로 | LingBot이 이미 dense 포인트를 주므로, COLMAP SfM의 sparse 대신 이걸 dense init으로 쓰면 3DGS가 훨씬 빨리 좋은 품질 수렴. (config `init_from_dense`) |
| **.splat 변환기를 직접 작성** | vanilla gaussian-splatting에는 .splat exporter가 없음. 학습 결과 `point_cloud.ply`(SH/opacity/scale/rot)를 웹 표준 .splat(32바이트/가우시안)으로 변환해야 함. |
| .splat 32바이트 레이아웃 | `pos(3f) + scale(3f, exp) + rgba(4u8) + rot(4u8)`. scale은 log→exp, 색은 SH DC(0.5+C0·f_dc), alpha는 sigmoid(opacity). antimatter15/gsplat 호환. 중요도 정렬로 점진 로딩. |

산출물: `03_3dgs/{colmap/, model/, output.splat}`

### Stage 4 — 웹 뷰어
파일: `stages/stage4_viewer.py` + `web/` (env: 무관)

| 설계 | 왜 |
|---|---|
| **@mkkellogg/gaussian-splats-3d** 채택 (gsplat.js 대신) | 요청은 "Three.js + gsplat.js"였지만, splat **위에 차량 메시 + 경로선 + 격자**를 한 씬에 얹고 애니메이션하려면 Three.js 네이티브 통합이 필요. gsplat.js는 splat 전용이라 일반 메시 합성이 까다로움. mkkellogg는 Three.js Object3D로 동작. (교체 가능하게 분리) |
| `DropInViewer`로 내 Three.js 씬에 추가 | 독립 Viewer를 쓰면 카메라/씬을 라이브러리가 독점. DropIn으로 받아야 격자·차량·경로를 같은 씬에 둘 수 있음. |
| `sharedMemoryForWorkers: false` | true면 COOP/COEP 헤더가 필요 → 단순 `python -m http.server`로는 안 뜸. 헤더 없이 열리게. |
| 회전 기본 없음(Y-up 그대로) | Stage 2에서 이미 Y-up 정렬했으니 splat·경로가 같은 좌표계. 뒤집혀 보이면 `splat_rotation`으로만 보정. |
| 차량을 **경로 접선 방향**으로 lookAt | 포즈의 카메라 회전 대신 인접 위치 차분(tangent)으로 진행방향 결정 — 더 안정적이고 "달리는" 느낌. |

산출물: `04_viewer/viewer/` (정적 서버로 열기)

## 3. 데이터 흐름 & 좌표계 규약 (한눈에)

```
MOV
 │  (env: lingbot-map)
 ▼ Stage1: LingBot inference
01_mapping/point_cloud.ply (월드, 첫프레임 기준, 기울어짐)
01_mapping/camera_poses.json (c2w 4x4, opencv 규약)
01_mapping/images/ (518 crop, intrinsics와 일치)
 │  (env: 3dgs_pipeline)
 ▼ Stage2: 강체변환 T (지면→Y=0)  ※ 포인트·포즈 동시 적용
02_preprocess/point_cloud_clean.ply (Y-up)
02_preprocess/camera_poses_aligned.json (Y-up)
 │
 ▼ Stage3: c2w→w2c, COLMAP, 학습, splat
03_3dgs/output.splat (Y-up, 웹 표준)
 │
 ▼ Stage4
04_viewer/viewer/ (splat + 경로 + 차량)
```
- 포즈 규약: `c2w` 4x4, 카메라 좌표 opencv(+x right, +y down, +z forward).
- Stage2 이후 월드는 **Y-up**(지면 Y=0). 이게 Three.js와도 맞음.

## 4. 왜 conda env를 둘로 나눴나

| env | torch | 담당 | 비고 |
|---|---|---|---|
| `lingbot-map` | 2.8.0+cu128 | Stage 1 | LingBot 요구. `setup/setup_lingbot_env.sh`로 생성 |
| `3dgs_pipeline` | 2.4.0+cu121 | Stage 2/3/4 + run.py | open3d/plyfile/diff-gaussian-rasterization 등 이미 구비 |

torch 2.8 ↔ 2.4가 한 env에 공존 불가. 그래서 `run.py`는 `3dgs_pipeline`에서 돌며
Stage 1만 **교차 호출**한다:
```
conda run -n lingbot-map python stages/stage1_infer.py --params params.json
```

## 5. 오케스트레이터 설계 (`run.py`)

- **컨벤션 기반 출력 디렉토리**: `01_mapping/ 02_preprocess/ 03_3dgs/ 04_viewer/`.
- 각 단계가 고정 위치에 쓰므로, `--stages 2,3,4`처럼 **일부만 재실행**해도
  이전 산출물을 자동으로 이어받음 (기존 12단계 파이프라인의 artifact-restore와 같은 철학).
- `--skip_train`으로 COLMAP 데이터셋만 만들어 빠르게 점검 가능.
